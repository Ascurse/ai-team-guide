## Visual-safe workflow для UI-задач

Проект использует контур для визуальной проверки UI до того, как агент считает задачу
завершённой. Актуальные инструменты и команды — смотри в `package.json`/CI-конфиге, а не в этом
файле: он описывает контракт, а не версии.

### Minimum visual DoD (обязательно перед "готово" по UI-задаче)

Проходится **по пунктам с явным ответом на каждый**, а не общим «проверил, всё в порядке»: перечень
и обход по нему — разные вещи, и на одном и том же контексте общий призыв даёт заметно худший
результат, чем зачитанный список.

- Есть story/route/фикстура, где изменённое состояние видно без ручного логина/сложного сетапа.
- Desktop-скриншот проверен агентом визуально (не только "код выглядит правильно").
- Mobile/адаптивный скриншот проверен для layout-компонентов.
- Нет обрезки/наложения текста, нет пустого iframe/root.
- Состояния loading/error/empty/success покрыты хотя бы story или integration-тестом.
- **Изменённые строки исполняются хотя бы одним тестом** — не «прогон зелёный». Это разные
  утверждения: у медианного PR, написанного агентом, покрытие собственного изменения нулевое.
  Если в проекте есть измерение покрытия по диффу — команда указана ниже; если нет — назови
  вслух тест, который проходит по изменённым строкам, или скажи, что такого нет.
- Если менялся snapshot-baseline — diff открыт и осознанно принят, а не проигнорирован.
- В консоли браузера нет новых ошибок/warning'ов, связанных с изменением.

### Обязательные проверки перед сдачей UI-задачи

```bash
<build-команда>       # например: yarn build
<lint-команда>         # например: yarn lint
<unit-test-команда>    # например: yarn test
<visual/e2e-команда>   # например: yarn test:e2e / yarn test:visual — если задача меняет layout/CSS
```

Если визуальный/e2e-раннер не запускался — агент обязан явно написать, почему (не "ой, забыл").

### Гейт может ответить "ничего не менять" — и это его дефолт

Проверка, обязанная выдать на выходе список правок, выдаёт его и тогда, когда всё в порядке, и
переписывает рабочий код. Поэтому:

- «Замечаний нет» — валидный и **ожидаемый по умолчанию** результат ревью/визуальной проверки.
  Пустой вывод — это успех гейта, а не невыполненная работа.
- Гейт **перенаправляет, а не выбрасывает**: при срабатывании задача продолжается с уже сделанного
  (правится конкретное место), а не начинается заново с чистого контекста. Перезапуск с нуля стоит
  дороже, чем даёт, и уничтожает работу тех прогонов, которые он оборвал ошибочно.
- Правку по замечанию, которая не подтверждена ничем, кроме мнения проверяющего, не применяй молча:
  либо воспроизведи дефект, либо оставь как есть и напиши, что замечание не подтвердилось.

### Известные ловушки (проверять всегда)

- **Динамическое время/id/анимации ломают снапшоты.** Не снапшотить компонент, читающий текущее
  время/случайные значения напрямую из глобального источника — сначала научить его принимать это
  как проп/из стора.
- **Baseline снапшотов платформозависим.** Baseline генерировать в том же окружении, что и CI
  (обычно Linux-контейнер), а не локально на macOS/Windows. Локальные baseline с другой ОС в git
  не коммитить.

### Если чего-то из контура не хватает

и дождаться подтверждения перед стартом.
