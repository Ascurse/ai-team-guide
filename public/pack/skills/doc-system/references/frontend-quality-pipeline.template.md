# Frontend Quality Pipeline — аудит-чеклист и фазовый план

Универсальный (framework-agnostic) чеклист и шаблон плана для UI-проектов, где агенты часто
ломают вёрстку/визуал, а обратная связь "агент увидел свою же ошибку" отсутствует. Не завязан
на конкретные инструменты — сначала определи, что уже используется в проекте, и расширяй именно
это, а не навязывай другой стек.

Эталонная реализация (полный пример на реальном стеке — React/Vite/Storybook/Playwright/Beads):
`client-backoffice`, `docs/playwright-implementation-plan.md` + Beads-эпик `client-backoffice-85s`.

## 0. Определить стек (не гадать)

Прочитать `package.json` (или аналог: `pyproject.toml`, `Gemfile` — если фронтенд не JS/TS-only) и найти:

- **Framework:** React / Vue / Angular / Svelte / другое.
- **Bundler/runner:** Vite / webpack / Next.js / CRA-наследие.
- **Unit/integration test runner:** Vitest / Jest / другое. Если есть — не заменять, а надстраивать.
- **Component workshop:** Storybook / Ladle / Histoire / нет.
- **Browser e2e:** Playwright / Cypress / нет.
- **Visual regression:** нативные screenshot-тесты раннера, либо внешний сервис (Chromatic, Percy,
  Loki, reg-suit), либо ничего.
- **CI:** GitHub Actions / GitLab CI / другое, и что в нём реально запускается (не то, что
  упомянуто в README — README может врать, сверяйся с самим конфигом и `package.json`).
- **Трекер задач:** Beads (`.beads/`) / Linear / Jira / Yandex Tracker / GitHub Issues / нет.

## 1. Аудит текущего состояния

Чеклист (да/нет/частично по каждому пункту, с указанием файла-доказательства):

- [ ] Unit/integration слой есть и зелёный.
- [ ] Есть способ узнать, покрыты ли тестами **изменённые строки** (coverage по диффу), а не только
      «весь прогон зелёный». Зелёный прогон при нулевом покрытии изменения — типовое состояние
      агентского PR, а не редкий случай.
- [ ] Component workshop есть, компоненты изолированно рендерятся с разными состояниями (loading/
      error/empty/success), а не только "happy path".
- [ ] Есть механический способ агенту **увидеть** рендер (headless browser + screenshot), а не
      только прочитать код.
- [ ] Визуальная регрессия: снапшоты есть, детерминированы (см. §3 про ловушки) и ревьюятся как код.
- [ ] E2E покрывает routing/auth/layout критичных сценариев, короткий и не флакующий.
- [ ] A11y-проверка встроена хоть в каком-то виде (лint-плагин, addon, автотест).
- [ ] CI реально гоняет lint/build/test (не только описано в доке).
- [ ] В `AGENTS.md`/аналоге прописан **minimum visual DoD** для UI-задач (см.
      `references/agents-quality-section.md`).
- [ ] В `AGENTS.md` нет устаревших/противоречащих факту утверждений о тест-раннере (частая
      находка: README/AGENTS.md один инструмент, а `package.json` — другой; сверяйся со вторым).

Если что-то отсутствует или "частично" — это не повод молча чинить всё за один проход. См. §4.

## 2. Фазовый план (обобщённый порядок, адаптируй пункты под найденный стек)

Порядок специально построен так, чтобы каждая фаза давала пользу сама по себе, а не требовала
завершения следующей:

1. **Стабилизировать то, что уже есть.** Если e2e/визуальный раннер уже добавлен, но не запускается
   (порт занят, browsers не установлены, webServer конфликтует) — почини именно это первым. Без
   зелёного базового прогона дальше двигаться бессмысленно.
2. **Задокументировать контракт.** Актуализировать `AGENTS.md`/README: какие команды реально
   работают, какой раннер актуален. Убрать враньё (устаревшие упоминания инструментов).
3. **Визуальный smoke от component workshop.** Не от живого бэкенда/полного приложения — от
   изолированных состояний компонентов. Компонентный workshop и screenshot-раннер обычно должны
   ходить в **разные serve-цели** (свой webServer/сервер для workshop, свой — для приложения) —
   не смешивать.
4. **Дать агенту быстрый visual workflow + minimum DoD.** Агент должен уметь за одну команду открыть
   изменённый экран/story, снять screenshot desktop+mobile, и явно отчитаться, что проверил.
5. **Расширить deterministic app-e2e.** Только бизнес-критичные сценарии, сети замоканы
   детерминированно. Каждый новый e2e должен отвечать на вопрос "какой дефект поймает браузер, но
   не поймает unit-слой/workshop?" — если ответа нет, тест не нужен на этом уровне.
6. **CI-гейты.** Сначала non-blocking/manual для визуального слоя, blocking — после подтверждённой
   стабильности (нет флака 1-2 недели). Build/lint/unit — blocking сразу, это не обсуждается.
   У каждого гейта должен быть дешёвый исход «ничего не менять»: молчание — валидный результат, а
   сработавший гейт возвращает к конкретному месту, а не отправляет задачу на перезапуск с нуля.

> **Примечание (single-source, на этот стек не измеряли).** Для механизма «агент увидел свою ошибку» (фаза 4) пиксельный скриншот — не единственный и не дешёвый путь. Структурные снапшоты (Playwright DOM/snapshot-ассерты, accessibility-tree) детерминированы и на порядки дешевле по токенам; пиксель-дифф оправдан только там, где рендер не выражается в структуре (canvas, WebGL, кастомная отрисовка). Держать как гипотезу, а не как доказанное правило.

## 3. Универсальные ловушки детерминизма (проверять всегда, независимо от стека)

1. **Динамическое время/id/random.** Любой компонент, показывающий относительное время
   ("через 5 минут"), тикающий таймер, случайный id — даст нестабильный снапшот. Компонент должен
   принимать текущее время/значение как проп/из стора, а не читать глобальный источник напрямую —
   иначе воркшоп-story для него завести нельзя без правки прод-кода.
2. **Анимации/transitions.** Замораживать через test-only CSS (`animation-duration: 0s !important`
   и т.п.), не трогая прод-стили.
3. **Платформенный суффикс baseline.** Screenshot-раннеры пишут baseline с суффиксом ОС
   (`-darwin` vs `-linux`). Если разработка на macOS, а CI — Linux-контейнер, baseline с mac всегда
   будет "missing" на CI. Правило: baseline генерировать **только** в том же образе/контейнере,
   что и CI; локальные mac-снапшоты в git не коммитить.
4. **Внешние виджеты/iframe/капча/чат.** Скрывать в test-only CSS — они недетерминированы и не
   контролируются проектом.

## 4. Если найден пробел — предложить задачи в трекере проекта, не чинить молча

Правило (применяется всегда, framework-agnostic):

1. Определить трекер проекта (§0). Если это Beads — использовать `bd`/`mcp__beads__*`, создать
   epic на весь пайплайн и task на каждую фазу из §2, с зависимостями между фазами (следующая
   блокируется предыдущей, если это реальная блокировка, а не просто порядок предпочтения).
   Приоритет: фазы 1–2 (стабилизация + документация контракта) — выше (P2), фазы 3–6 — обычно P3,
   если продукт явно не горит визуальными регрессиями прямо сейчас.
2. Если трекер другой (Linear/Jira/Yandex Tracker/GitHub Issues) — предложить тот же набор
   epic+tasks в терминах этого трекера через доступный MCP/CLI, не переизобретая Beads-специфичные
   поля.
3. Если трекера нет вообще — не создавать самовольно md-план с бессрочным статусом. Показать
   предложенный список фаз пользователю и спросить, где его вести (новый файл, issue-tracker,
   просто в разговоре) — не выбирать самостоятельно.
4. Не создавать все фазы сразу как "в работе" — предложить, показать порядок и приоритеты,
   дождаться подтверждения перед стартом первой фазы (кроме тривиальных read-only аудитов).
5. Один и тот же аудит не должен порождать дублирующиеся epic/tasks при повторном запуске —
   сначала проверить существующий трекер (`bd list`/`bd ready`/аналог) на уже заведённые
   фазы/эпик этого же пайплайна.

## Что НЕ делать

- Не менять существующий выбор инструмента (не тащить Playwright в проект на Cypress "потому что
  так лучше") без явного запроса.
- Не включать визуальный CI-гейт как blocking сразу — это гарантированно даст флак на старте.
- Не строить гейт, который обязан вернуть непустой список замечаний или отправить задачу на
  перезапуск с нуля. Проверка без дешёвого выхода «всё в порядке» начинает переписывать рабочий код.
- Не гнаться за 100% визуальным покрытием — начинать с 3–6 самых частых/критичных UI-паттернов
  проекта.
- Не путать этот чеклист с самим `docs/journal/` — сюда пробелы качества, в journal — находки и
  решения после того, как пробел закрыт.
