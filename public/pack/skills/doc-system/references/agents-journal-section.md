## Общая память проекта (`docs/journal/`)

Закоммиченная память, общая для всех людей и AI-инструментов. Не путать с личной памятью отдельного агента — она остаётся у каждого своя.

### Файлы

- [docs/journal/decisions.md](docs/journal/decisions.md) — ключевые архитектурные решения (lightweight ADR).
- [docs/journal/gotchas.md](docs/journal/gotchas.md) — подводные камни и нетривиальные нюансы.
- [docs/journal/glossary.md](docs/journal/glossary.md) — доменный словарь.

Это **исчерпывающий** список того, что читает агент. Если в `docs/journal/` есть `gotchas-archive.md` / `decisions-archive.md` — это архив для аудита людьми, **агент его не читает и не грепает**; он не входит ни в один из пунктов ниже.

### Что обязан делать AI-агент

**Перед нетривиальной задачей:**

1. Прочитать `docs/journal/decisions.md` — могут быть актуальные решения, противоречащие текущему запросу.
2. Прочитать `docs/journal/gotchas.md` — возможно, грабли уже задокументированы.
3. При незнакомом термине — заглянуть в `docs/journal/glossary.md`.

**Перед правкой конкретного файла (точечный retrieval):**

Записи в `gotchas.md` снабжены ссылками «Где это в коде» — это обратный индекс «файл → грабли по нему». Перед изменением файла `X` сделай `grep -rn "X" docs/journal/decisions.md docs/journal/gotchas.md docs/journal/glossary.md` (по имени или пути файла; архивные файлы в поиск не включай). Если по нему есть запись — прочитай её до правки. В Claude Code этот греп делает PreToolUse-хук `.claude/hooks/journal-retrieval.py` и подмешивает записи сам; в остальных инструментах — вручную. Это дешевле и надёжнее, чем читать весь журнал целиком: нужная запись находится ровно тогда, когда нужна.

Ссылка вида `путь:символ @ <SHA>` означает, что запись проверялась против этого коммита. Нашёл такую запись — сразу проверь `git log <SHA>..HEAD -- <путь>`: если файл с тех пор менялся, запись может быть устаревшей, и это надо учесть в правке (а если она устарела точно — обновить или снять по правилам ниже). Отдельным проходом по журналу это гонять не надо.

**После нетривиальной находки** (новый сюрприз библиотеки, обоснованное архитектурное решение, новый бизнес-термин):

- Дописать короткую запись (1–4 предложения на поле, не хроника работы: без номеров веток/бидов, без пошагового пересказа) в соответствующий файл — **в тот же ход, в котором сделана находка**, а не в конце задачи. Между находкой и «подведу итоги» стоит компакция контекста: она факты почти не переносит, поэтому запись, оставшаяся в трассе, теряется целиком. Одна находка — одна запись, накапливать и записывать разом нельзя.
- Если запись про конкретный код — в «Где это в коде» ставь якорь `путь:символ @ <SHA текущего коммита>`. Если запись не про код — якоря нет, выдумывать не надо.
- Необязательно: если в окружении есть `jev`, перед записью прогони черновик через `python3 ~/.agents/skills/doc-system/scripts/journal-jev.py check < черновик.md`. Он подскажет, не место ли этому в комментарии рядом с кодом и нет ли уже похожей записи. Это совет, не запрет: нет `jev` — пиши как обычно.
- Отдельный триггер для `decisions.md`: **отклонили формально верное замечание ревью, потому что «так сделано намеренно»**. Это самая частая причина, по которой корректное замечание не применяют; пока решение нигде не записано, следующий человек или агент предложит ровно то же самое снова.
- Дата в формате `YYYY-MM-DD`, новые записи — сверху.
- Если запись пересматривает старую и обе ещё короткие/актуальные — старую не удалять, пометить `[пересмотрено: YYYY-MM-DD]`.
- Если факт/обход устарел целиком — **удали** запись, если она не объясняет полезный контекст (почему был нужен костыль); иначе перенеси в `docs/journal/gotchas-archive.md` (или `decisions-archive.md`) с меткой `[снято: YYYY-MM-DD]`. Активный файл не должен расти — устаревшее там не задерживается.

### Что НЕ хранить в journal

- Текущую работу, статус веток, in-progress задачи (это в git, PR и трекере).
- Пояснение «почему так» к одному месту в коде — ему место в комментарии рядом с этим кодом, агент прочитает его вместе с файлом. В журнал идёт то, что охватывает несколько файлов или не видно ни из одного.
- Длинные мануалы — для них есть `docs/<topic>.md`.
- Дубли того, что уже написано в `AGENTS.md`.
- Личные предпочтения отдельных разработчиков.

### Per-branch контекст

Отдельных файлов на каждую ветку **не заводим** — это плодит мердж-конфликты и дублирует git. Branch-specific информация живёт в commit-сообщениях, описании PR/MR и `CHANGELOG.md`. В `docs/journal/` попадает только то, что переживёт ветку.
