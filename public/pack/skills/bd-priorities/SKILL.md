# bd-priorities

Собирает состояние beads-трекера текущего проекта одним батчем команд и выдаёт текстовый отчёт: в каком порядке брать готовые задачи, что разблокирует больше всего работы, что можно раздать параллельно субагентам, и что подгнило (зависло, потеряно, без описания).

Только анализ и рекомендация — никаких `bd update`/`bd close` от имени скилла. Решение о захвате задачи остаётся за основным агентом/пользователем.

## Когда использовать

- Пользователь спрашивает «что делать дальше», «какие задачи в приоритете», просит порядок выполнения bd-задач
- Явный вызов `/bd-priorities`
- Нет активного beads-воркспейса (`.beads/` в проекте) → сказать об этом и предложить `bd init`, дальше не выполнять

## Шаг 1 — собрать данные (один Bash-вызов)

```bash
bd ready --json --brief --exclude-type epic
bd ready --explain --json
bd list --type=epic --status=open --no-parent --json --brief
bd stale --json
bd list --empty-description --json --brief
bd orphans --json
```

`--brief` (beads ≥1.2.0) выкидывает из каждой строки description/design/acceptance/notes/payload — для ранжирования они не нужны, а вывод короче примерно вдвое (замер: 37K → 16K на 20 ready-задачах). `dependent_count`, `priority`, `parent`, `labels` остаются. Флаг работает **только вместе с `--json`** и **только** у `bd ready` и `bd list`: с `--explain` он даёт ошибку («--explain cannot be combined with --brief»), а `bd stale`, `bd orphans` и `bd children` его не знают вовсе (`unknown flag`) — там оставить как есть.

Две команды `bd ready` нужны обе — у `--exclude-type` есть баг: он работает в обычном `bd ready --json`, но **игнорируется** при добавлении `--explain`. Поэтому:
- **Список ready-задач** (что реально брать в работу, с `dependent_count`) — бери из первой команды (`--exclude-type epic`, без эпиков).
- **Секцию `blocked`** (с `blocked_by` — кто и почему держит) — бери из второй команды (`--explain`). Её `ready`-секцию игнорируй — там эпики не отфильтрованы.

Если в `list --type=epic` нашлись открытые эпики верхнего уровня — для каждого дополнительно:
```bash
bd children <epic-id> --json
```
(включает закрытые дети — считать `closed/total` для прогресса).

## Шаг 2 — рубрика ранжирования ready-задач

Сортировать без отдельной формулы, по убыванию значимости:

1. **Приоритет** (P0 → P4) — основная ось, как в самом `bd ready`
2. **Внутри приоритета** — выше та, у кого больше `dependent_count` (разблокирует больше других)
3. **При равенстве** — выше та, чей `parent`-эпик ближе к завершению (closed/total из шага 1)
4. Если задача есть и в `ready`, и в `bd stale` — пометить `⏳ висит N дней`, но **не** менять её место в порядке из-за этого — только флаг

## Шаг 3 — отчёт (текст в чат, без файлов)

```
## Рекомендуемый порядок
1. Developer-yow.1 [P0] TESTFIXTURE A — разблокирует 2 задачи · эпик "Alpha" (0/4)
2. Developer-yow.2 [P1] TESTFIXTURE B
...

## Разблокировщики
- Developer-yow.1 → откроет Developer-yow.3, Developer-yow.4

## Параллельные группы (можно раздать субагентам)
Все задачи из ready — уже взаимно независимы (иначе не были бы ready).
Группа: Developer-yow.1, Developer-yow.2, Developer-s7q (не пересекаются по зависимостям)

## Прогресс по эпикам
- Alpha: 0/4 закрыто

## Требует внимания
- Зависшие (>30 дней): нет / список
- Похоже сделано, но не закрыто (orphans): нет / список
- Без описания: N задач (если N ≤ 5 — перечислить все; если больше — только count + первые 5)
```

Если `ready` пуст — сказать явно и показать топ заблокированных (кто и чем блокирован), не выдумывать план.

## Частые ошибки

- **Путать `dependent_count` с числом детей.** Это только "blocks"-зависимости — сколько задач реально разблокируется, не `parent-child`.
- **Заливать весь `--empty-description`/`bd lint` в отчёт.** Почти в любом проекте это половина трекера — показывать count + до 5 примеров (или все, если их и так ≤5), не сырой полный список.
- **Пускать сам эпик в рекомендуемый порядок задач.** У эпика тоже нет блокировщиков, поэтому он технически "ready" — но это контейнер, не работа для захвата. Именно поэтому ready-список для ранжирования берётся из вызова с `--exclude-type epic`.
- **Использовать `bd list --status=blocked` для поиска заблокированных.** Статус `blocked` не проставляется автоматически при добавлении зависимости — источник истины это `blocked` из `bd ready --explain --json`.
- **Переставлять задачи местами из-за staleness.** Устаревшая ready-задача не становится менее приоритетной — это просто повод спросить пользователя, актуальна ли она ещё.
