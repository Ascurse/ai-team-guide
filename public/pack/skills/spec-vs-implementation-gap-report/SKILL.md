# spec-vs-implementation-gap-report — сверка реализации с внешним документом

Сверить текущую реализацию с эталонным документом (инструкция интеграции от бэка, план MVP, задача
в трекере) и выдать отчёт по фиксированной структуре: что готово, что частично, чего нет, блокеры.

## Когда запускать

- «Проверь, всё ли мы реализовали по инструкции», «что сделано и чего не хватает по плану MVP».
- Подготовка к созвону по статусу или проверка перед сдачей.
- Отличие от `project-discovery`: тот извлекает конвенции/архитектуру проекта; здесь — сверка с **внешним**
  документом и отчёт для заказчика/владельца продукта.
- Отличие от `bd-priorities`: тот про здоровье трекера и «что делать дальше». Этот скилл нужен только когда
  есть **внешний эталон** для сверки; без документа/плана — это не сюда.

## Шаги (не пропускать)

### 1. Получить эталон
Документ/план/тикет — как список проверяемых требований. Если это ссылка на `tracker.yandex.ru` — вытащить
через MCP `yandex-tracker` (`tracker_get_issue`); если тулы deferred — сначала `ToolSearch` (`select:...`).
Разбить эталон на отдельные пункты-требования.

### 2. Построить карту реализации (Explore-субагент)
Поднять `Explore`, чтобы найти, где каждое требование реализовано (или нет) — дешевле, чем читать всё
в основном контексте. Смотреть на факт в коде, не на память.

### 3. Построчная сверка
Каждый пункт эталона → статус по факту кода, с указанием файла/места как доказательства.

### 4. Отчёт по фиксированной структуре
Выдать ровно в таком виде (это контракт вывода, а не вольный текст):

```
## ✅ Готово
- <пункт> — <файл/место>

## 🟡 Частично
- <пункт> — что есть, чего не хватает

## ❌ Не реализовано
- <пункт> — почему (не начато / блокер)

## ⛔ Блокеры / вопросы
- <что мешает или требует решения на созвоне>
```

Отчёт выдаётся **в ответ в чат** — это не файл, не класть в scratchpad/репозиторий.

### 5. Завести задачи под пробелы (по согласованию)
Если по итогам есть пункты «частично»/«не реализовано», требующие доработки — по согласованию с
пользователем завести под них `bd`-задачи (см. `beads-workflow`). Сама сверка — это нетривиальное
исследование, поэтому под неё бид тоже уместен.

## Проверка (verification-before-completion)

- Каждый пункт эталона попал ровно в одну секцию отчёта — ничего не потеряно.
- Статусы подтверждены ссылкой на код (Explore), а не догадкой.
- «Частично» всегда содержит «чего именно не хватает».

## Запреты

- Не пересказывать сам документ вместо сверки — отчёт про **разницу**, а не про эталон.
- Не отмечать «готово» без подтверждения в коде.
