# bd-branch-integration-merge — пакетное слияние bd-веток в интеграционную

Смёржить N готовых `bd-*` веток (сделанных субагентами в отдельных воркчтри) в одну общую
feature/интеграционную ветку. Порядок операций строгий — его легко нарушить.

## Когда запускать

- Несколько задач `bd-*` реализованы и запушены, нужно свести их в общую ветку (`feature/…`).
- Просьбы «смержи bd-X и bd-Y в feature/…», «пуш все bd-* и вмержи их», «ретаргетни зависимую».
- **Не** про одиночную ветку своим исполнителем (это `beads-workflow`) и **не** про чистку stale-веток (`/quick cleanup`).

## Ключевое правило: порядок по зависимостям

Мержить в порядке зависимостей — **база раньше зависимой**. Влить зависимую ветку до её базы —
самая частая ошибка. Если `bd-B` строился поверх `bd-A`, сначала `bd-A` → потом ретаргет `bd-B` → потом `bd-B`.

## Шаги (не пропускать) — по одной ветке за раз

### 1. Запушить всё
`git push origin bd-…` для каждой ветки, которую сводим.

### 2. Staleness-проверка перед мержем
`git diff <feature>...bd-…` (три точки) — не только `git log`. Ловить **дизайн-конфликты**, а не только
merge-конфликты: feature-ветка могла уйти вперёд с момента расхождения. Спорное — флагнуть, не мержить вслепую.

### 3. Влить одну ветку
Сперва обновить локальную базу: `git fetch origin && git checkout <feature> && git pull origin <feature>`.
Затем `git merge --no-ff origin/bd-… -m "merge(bd-…): …"`.

### 4. Перепрогнать проверки (lint/build/test) на результате
lint / build / test на **смердженном** дереве. Красное — чинить до следующей ветки, не копить.

### 5. Ретаргетнуть зависимые
Ветку, которая строилась на только что влитой, ретаргетнуть на обновлённую feature. По умолчанию —
безопасный merge, сохраняющий историю: в воркчтри зависимой ветки `git fetch origin && git merge origin/<feature>`.
Rebase (`git rebase origin/<feature>` + `git push --force-with-lease`) — **только** если ветка ещё не
расшарена и пользователь явно согласен на переписывание истории. Затем вернуться к шагу 2 уже для неё.

### 6. Убрать воркчтри и закрыть бид
`bd worktree remove .worktrees/bd-{ID}` (НЕ raw `git worktree`, симметрично `bd worktree create`) →
`bd close {ID} --reason "Merged into <feature> (<hash>)"`.

Повторять 2–6 для каждой ветки в порядке зависимостей.

Почему по одной, а не пачкой: воркчтри снимает конфликт записи в дерево, но не конфликт интеграции —
до детерминированного контроля допуска треть интеграций падала даже при полностью изолированных
воркчтри; с гейтом на мерже pair pass 23.3% → 50.0%, integration success 65.6% → 96.7%, ценой
сериализации. Шаги 2 и 4 — это и есть тот гейт, пропускать их ради скорости нельзя.

## Защищённые ветки

Если `<feature>` — это `master`/`main`/`production`/деплой-ветка: **не пушить напрямую** даже после чистого
мержа. Подтвердить с пользователем или открыть MR/PR.

## Проверка (verification-before-completion)

- Ветки влиты в порядке зависимостей; зависимые ретаргечены на обновлённую базу.
- Проверки (lint/build/test) зелёные на **финальном** смердженном дереве, а не по-отдельности.
- Воркчтри убраны через `bd worktree remove`; биды закрыты с reason и хешем мержа.
- В защищённую ветку напрямую не пушили без подтверждения.

## Запреты

- Не мержить зависимую ветку раньше её базы.
- Не пушить напрямую в защищённую ветку (`master`/`main`/`production`/деплой) без подтверждения.
- Не использовать raw `git worktree remove` — только `bd worktree remove`.
- Не копить красные проверки между ветками — чинить до следующей.
- Rebase уже расшаренной ветки без явного согласия — запрещён (переписывает историю).
