# dependency-major-upgrade — мажорный апгрейд зависимости

Оценка и выполнение перехода на мажорную версию библиотеки. Устойчивый порядок: сперва независимая
оценка «стоит ли», потом разбиение по зоне поражения кода, потом обязательный проход по типам/сборке.

## Когда запускать

- «Стоит ли обновлять X до мажора?», «берёмся за миграцию, раскидай по субагентам».
- «Почини type errors после мажорного апгрейда», «close … as won't migrate».
- Отличие от `dispatching-parallel-agents`: здесь структура этапов конкретная (оценка → зона поражения →
  миграция → типы), а не общий приём раздачи задач.

## Инструменты

- **Context7** (MCP): `resolve-library-id` → `query-docs` для changelog/breaking changes. Если тулы
  deferred — сначала `ToolSearch` (`select:...`).
- **Задачи**: `bd` — эпик миграции + подзадачи по кускам.

## Шаги (не пропускать)

### 1. Оценить целесообразность
Через **Context7** (`resolve-library-id` → `query-docs`) поднять changelog/breaking changes. Оценить объём
поражения (какие места кода задеты), выигрыш и риск. Отдельный вывод: **мигрируем** или **не мигрируем**.

### 2. Зафиксировать решение
- **Не мигрируем** — это валидный исход: закрыть бид `bd close … --reason "won't migrate: <причина>"`.
- **Мигрируем** — дальше по шагам.

### 3. Разбить по зоне поражения
Поделить работу **по области кода** (компонент/модуль/файл), где встречается старое API, — так, чтобы
куски были независимы и не конфликтовали при параллельной правке. Завести эпик и подзадачи:
`bd create ... --type epic` на миграцию, `bd create --parent <epic>` на каждый кусок.

### 4. Параллельная миграция субагентами
Раздать куски субагентам (модель — дешевле топовой; конкретный ID взять из текущего указания в
глобальном `AGENTS.md`, не хардкодить снапшот), каждому — тайтл вида «Migrate <область> to <version>».
При параллельной правке файлов изолировать каждый кусок через `bd worktree create .worktrees/bd-{ID}
--branch bd-{ID}` (НЕ raw `git worktree` — см. `beads-workflow`).

### 5. Обязательный проход по типам и сборке
После миграции — собрать возникшие type errors и build-ошибки и починить их. Это отдельный шаг, его нельзя
пропускать: параллельные куски по-отдельности зелёные, а вместе дают ошибки на стыках.

### 6. Завершить
Коммит/пуш/мерж по воркфлоу проекта (при нескольких кусках — см. `atomic-commit-split`; при нескольких
ветках — `bd-branch-integration-merge`).

## Проверка (verification-before-completion)

- Решение «мигрируем/не мигрируем» обосновано changelog'ом (Context7), а не наугад.
- После миграции пройден отдельный проход: type-check и build зелёные на собранном результате.
- «won't migrate» закрыт в `bd` с причиной.

## Запреты

- Не начинать миграцию, не оценив breaking changes и объём поражения.
- Не считать работу готовой, пока не пройден проход по типам/сборке на объединённом результате.
- Субагентам не наследовать топовую модель — передавать дешевле явно.
